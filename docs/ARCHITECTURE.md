# Архитектура

Три приложения, одна база. Сайт и админка не общаются напрямую — только через API
бэкенда.

```
                    ┌──────────────┐
     посетитель ───▶│  web (3000)  │──┐
                    └──────────────┘  │  HTTP (публичные эндпоинты)
                                      ▼
                    ┌────────────────────────────┐     ┌────────────┐
                    │      backend (8000)        │────▶│ PostgreSQL │
                    │  FastAPI + SQLAlchemy      │     └────────────┘
                    └────────────────────────────┘
                                      ▲   │  файлы
     контент-менеджер ──▶┌─────────────┴┐  ▼
                         │ admin (3001) │ ┌────────────────┐
                         └──────────────┘ │ MinIO / S3     │
                                          └────────────────┘
```

---

## Backend (`backend/`)

FastAPI + SQLAlchemy 2.0 в синхронном режиме. Структура намеренно плоская: одна
`models.py`, одна `schemas.py`, роутеры по назначению. Проект небольшой, и
дробление на пакеты добавляло бы навигации больше, чем убирало сложности.

```
app/
├── main.py        сборка приложения, lifespan: create_all → DDL-патчи → seed
├── config.py      все настройки через ENV (pydantic-settings)
├── db.py          engine, SessionLocal, get_db
├── models.py      все таблицы
├── schemas.py     все Pydantic-схемы (In/Out)
├── security.py    JWT, хеш паролей, зависимости ролей
├── storage.py     абстракция хранилища файлов: LocalStorage | S3Storage
├── notify.py      уведомления о заявках в Telegram
├── redirects.py   инварианты 301-редиректов (петли, цепочки)
├── slug.py        транслитерация и нормализация слагов
├── sanitize.py    очистка HTML из rich-полей админки
├── seed.py        идемпотентный seed контента и учёток
└── routers/
    ├── public.py      публичное чтение (settings, contacts, analytics, banner…)
    ├── content.py     ФАБРИКА CRUD-роутеров — см. ниже
    ├── admin.py       планировки, статистика, health, учётки
    ├── leads.py       приём заявок + админ-обработка
    ├── media.py       загрузка/список/удаление + раздача `/media/{name}`
    ├── calc.py        расчёт рассрочки
    ├── seo.py         мета-теги страниц
    └── redirects.py   301-редиректы
```

### Фабрика контент-роутеров

`content.py::make_content_router` порождает одинаковый CRUD для 11 сущностей
(новости, документы, FAQ, преимущества, партнёры, команда, факты, тексты секций,
главы hero, категории планировок…): публичный `GET`, админские
`GET/POST/PUT/DELETE` и `POST /reorder`. Индивидуальное поведение подключается
хуками:

- `before_write(db, payload, existing)` — валидации и побочные эффекты записи
  (например, пометка «Политика обработки данных» может быть только у одного
  документа, и снять её у единственного активного нельзя — 409 `policy_required`);
- `before_delete(db, item)` — то же для удаления;
- `annotate(db, items)` — обогащение выдачи одним запросом (счётчик планировок
  в категории), без N+1;
- `public_prefix` — публичный путь, если он отличается от админского.

Добавить новую управляемую сущность = модель + схемы + одна строка регистрации
фабрики + конфиг в админке. Отдельный роутер писать не нужно.

### Схема базы: без Alembic

Схему создаёт `Base.metadata.create_all`, а изменения существующих таблиц —
блок идемпотентных DDL-патчей в `main.py` (`ADD COLUMN IF NOT EXISTS`,
нормализация данных). Причина: у проекта один инстанс и один разработчик,
и цена ветвящейся истории миграций выше пользы. Правило при изменении схемы:

1. Правишь `models.py`.
2. Если таблица уже существует в проде — добавляешь патч в `main.py`.
   Патч обязан быть идемпотентным: он выполняется при каждом старте.
3. Правишь `seed.py`, если у поля должно быть осмысленное начальное значение.

`seed.py` тоже идемпотентен: он не перезатирает то, что менял контент-менеджер,
а досоздаёт недостающее.

### Хранилище файлов

`storage.py` прячет за одним интерфейсом локальный диск и S3/MinIO — выбор через
`MEDIA_BACKEND`. В базе всегда лежит **относительный** путь `/media/<имя>`, а не
абсолютный URL: иначе при смене домена или порта все картинки разом ломаются
(так и случилось при переносе базы из другого проекта). Абсолютный адрес
собирается на лету — сайтом при рендере, админкой при показе.

Файлы отдаёт сам бэкенд (`GET /media/{name}`) с иммутабельным кэшем; сайт
проксирует их через свой путь `/cms-media/*`, чтобы браузер видел один домен.

Удаление файла проверяет, не используется ли он: поиск ссылок по восьми колонкам
контента, и при попадании — 409 со списком «где используется».

### Роли

Две роли: **суперадмин** (всё) и **менеджер** (контент и заявки, без настроек,
SEO, редиректов и калькулятора). Проверка на уровне зависимостей FastAPI, а не в
UI — админка лишь прячет пункты меню.

## Сайт (`web/`)

Next.js 15 App Router, серверные компоненты. Внутри — гексагональная архитектура:
зависимости направлены только внутрь, `presentation → application → domain`, а
`infrastructure` реализует порты приложения.

```
src/
├── domain/          сущности, value-objects, доменные сервисы (расчёт рассрочки)
├── application/     порты (интерфейсы репозиториев) + use-cases → view-модели
├── infrastructure/  адаптеры: api/ (репозитории поверх бэкенда) + content/ (статика)
├── composition/     container.ts — единственное место сборки зависимостей
└── presentation/    React-компоненты, hero-скраб, секции, стили
app/                 тонкий слой Next: роуты композируют секции
```

Смысл слоёв здесь не в церемонии, а в двух конкретных свойствах:

**Сайт работает, даже если API лёг.** У каждого порта есть два адаптера: API и
статический. Списочные страницы деградируют на статический контент вместо белого
экрана. А вот детальные страницы при недоступном API отдают честную 5xx, а не
404 — иначе поисковик выкинет живые страницы из индекса, приняв аварию за
удаление.

**Данные приходят в компоненты уже готовыми.** Use-case возвращает
сериализуемую view-модель; компонент не знает, откуда она — из CMS или из
статики. Поэтому «сделать блок управляемым из админки» — это подмена адаптера,
а не переписывание вёрстки.

Кэширование — ISR: ответы API кэшируются с `revalidate`, страницы
перегенерируются в фоне. Свежесть контента после правки в админке — до минуты.

### SEO-контур

- `composeMetadata` собирает мета-теги: CMS-значение → значение страницы →
  дефолт; полный Open Graph и Twitter-карточка, canonical, `noindex` из админки.
- JSON-LD: Organization и WebSite в layout, BreadcrumbList на всех внутренних
  страницах, FAQPage на главной, NewsArticle на новости, Product + Offer на
  планировке, ItemList в каталоге. Строится из уже загруженных данных — ни
  одного дополнительного запроса.
- `sitemap.ts` — реальные даты изменения из базы, без страниц с `noindex`;
  `robots.txt` — отдельный блок для Яндекса с `Clean-param` для UTM-меток.
- Смена слага в админке автоматически заводит 301-редирект со старого адреса.
  Резолвинг редиректа происходит в точке промаха (перед `notFound()`), а не в
  middleware: живые страницы не платят за это ничего, и живая страница всегда
  выигрывает у устаревшего редиректа.

## Админка (`frontend-admin/`)

Next.js без UI-фреймворка. Ключевое решение — **разделы описываются конфигом, а
не версткой**: `app/lib/resources.tsx` содержит описание полей и колонок для
каждой сущности, а `ResourceList` и `ResourceForm` рендерят по нему список и
форму. Новый раздел — это объект конфига и три страницы-обёртки по три строки.

```
app/
├── lib/
│   ├── resources.tsx     конфиги всех разделов (поля, колонки, валидации, хуки)
│   ├── api.ts            HTTP-клиент админки, ApiError с телом ответа
│   ├── errors.ts         коды ошибок бэкенда и 422 → русский текст
│   ├── validation.ts     клиентские проверки: все ошибки формы разом
│   ├── slug.ts           транслитерация (зеркало backend/app/slug.py)
│   ├── useUnsavedGuard   защита от ухода с несохранённой формы
│   ├── useAutoSlug       слаг печатается сам из названия, пока его не правят руками
│   ├── media.ts          относительный путь из базы → абсолютный URL картинки
│   └── site.ts           ссылки «Посмотреть на сайте»
└── components/           ResourceList, ResourceForm, MediaPicker, Toast, Checkbox…
```

### Конвенции, которые легко нарушить

**Проценты.** API хранит доли (`0.3`), админка показывает проценты (`30`).
Конверсия — строго на границе формы (`percent: true` у поля). Если забыть, можно
ввести «8» и получить 800 % годовых.

**Слаги.** Транслитерация на клиенте должна совпадать с `backend/app/slug.py`.
При правке одного правь и второе, иначе админка покажет один адрес, а сайт
отдаст другой.

**Инварианты контента защищает бэкенд, а не форма.** Единственная активная
Политика, шесть глав hero, занятый медиафайл — всё это 409 с кодом, который
админка переводит в человеческий текст. Клиентские проверки — для удобства,
а не для целостности.

## Заявки

Форма на сайте → `POST /api/v1/leads` → запись в базу → фоновая задача шлёт
уведомление в Telegram со ссылкой прямо на заявку в админке. Вместе с заявкой
сохраняются UTM-метки и снимок расчёта рассрочки (`calc_snapshot`: что ввёл
посетитель и что посчитал калькулятор) — чтобы менеджер видел, на какие условия
человек рассчитывал.

Отправка уведомления не блокирует ответ посетителю: если Telegram недоступен,
заявка всё равно сохранена, а ошибка уходит в лог.
